## Как развернуть локально

### Необходимое ПО

Для запуска ПО вам понадобятся консольный Git и Make. Инструкции по их установке ищите на
официальных сайтах:

- [Git SCM](https://git-scm.com/)
- [GNU Make](https://www.gnu.org/software/make/)

Вы можете проверить, установлены ли эти программы с помощью команд:
```shell
$ git --version
git version 2.37.1.windows.1

$ make --version
GNU Make 4.4.1
Built for Windows32
<...>
```

Для тех, кто использует Windows необходимы также программы **git** и **git bash**. В **git bash** необходимо дополнительно установить
**make**:

- Перейдите на сайт [ezwinports](https://sourceforge.net/projects/ezwinports/files/)
- Скачайте `make-4.4.1-without-guile-w32-bin.zip` (выберите версию без `guile`)
- Извлеките архив
- Скопируйте содержимое архива в `C:\ProgramFiles\Git\mingw64\` **БЕЗ** перезаписи/замены любых вложенных файлов.

Все дальнейшие команды запускать из-под **git bash**.

#### WSL (альтернатива)

Если вы предпочитаете использовать Windows Subsystem for Linux (WSL), установите Ubuntu из Microsoft Store и работайте из терминала WSL.

В WSL доступны все стандартные команды Linux, поэтому дополнительная настройка **make** не требуется.

Все дальнейшие команды запускать из терминала **WSL**.

### Создание виртуального окружения для работы с IDE

IDE для корректной работы подсказок необходимо развернуть виртуальное окружение со всеми установленными зависимостями.

В качестве пакетного менеджера на проекта используется [uv](https://docs.astral.sh/uv/).

[Установите uv](https://gitlab.dvmn.org/root/fastapi-articles/-/wikis/Uv-package-manager#1-%D1%83%D1%81%D1%82%D0%B0%D0%BD%D0%BE%D0%B2%D0%BA%D0%B0-uv) и в корне репозитория выполните команду

```shell
$ uv sync
```

[uv](https://docs.astral.sh/uv/) создаст виртуальное окружение, установит необходимую версию Python и все необходимые зависимости.

После этого активируйте виртуальное окружение в текущей сессии терминала:

```shell
$ source .venv/bin/activate  # для Linux
$ .\.venv\Scripts\activate  # Для Windows
```

Признак, что окружение активно: в начале приглашения терминала появляется
префикс `(venv)`:

```shell
(venv) user@host:~$
```

### Проверка установленных зависимостей

После выполнения команды `uv sync` убедитесь, что зависимости установлены корректно.

Сообщение об успешной установке выглядит так:

```shell
$ uv sync
Resolved 33 packages in 1.3s
Installed 33 packages
```

`Resolved 33 packages` — uv определил список пакетов по `pyproject.toml`,
`Installed 33 packages` — они установлены в виртуальное окружение. Число пакетов
сверяйте со своим проектом — оно зависит от количества зависимостей.

Выведите список установленных пакетов:

```shell
$ uv pip list
aioboto3 15.5.0
fastapi 0.115.12
ruff 0.11.13
```

Колонки — название пакета и его версия. Версии должны совпадать с указанными в
`uv.lock`: для каждого пакета в `uv.lock` фиксируются название (`name`) и версия
(`version`), например:

```toml
[[package]]
name = "aioboto3"
version = "15.5.0"
```

Совпадение списка `uv pip list` со списком в `uv.lock` означает, что зависимости
установлены верно. После этого запустите бекенд (см. «Схема приложения») — он
должен стартовать без ошибок.

### Проверка версии Python

Убедитесь, что активная версия Python совпадает с указанной в `pyproject.toml`:

```shell
$ python --version
Python 3.13.x
```

В начале файла `uv.lock` также зафиксирована требуемая версия Python:

```toml
requires-python = "==3.13.*"
```

Она должна совпадать со значением `requires-python` в `pyproject.toml` — uv
использует это значение для выбора версии Python при создании окружения.

### Изменение версии Python

Версия Python проекта задаётся в `pyproject.toml`:

```toml
requires-python = "==3.13.*"
```

Чтобы перейти на новую версию Python, например 3.14:

1. Укажите новую версию в `pyproject.toml`:
   ```toml
   requires-python = "==3.14.*"
   ```
2. Зафиксируйте её для проекта (uv сам скачает версию, если она ещё не
   установлена в системе):
   ```shell
   $ uv python pin 3.14
   ```
3. Пересоберите виртуальное окружение:
   ```shell
   $ uv sync
   ```

Проверьте результат:

```shell
$ python --version
Python 3.14.x
```

В `uv.lock` в начале файла версия также обновится:

```toml
requires-python = "==3.14.*"
```

Загруженная uv версия Python отличается от установленной в системе — uv хранит
скачанные версии в собственном каталоге (например, `~/.local/share/uv/python/`)

### Файл .env с переменными окружения

Переменные окружения задаются в файле `.env` в корневой папке репозитория.

Создайте файл:

```shell
$ touch .env
```

Заполните его переменными в формате `KEY=VALUE`.

Файл `.env` уже добавлен в `.gitignore` — он не попадёт в коммит. Убедиться в этом можно с помощью `git status`: файл `.env` не будет присутствовать в списке изменённых.

После коммита и отправки изменений в origin проверьте последний коммит в репозитории — файл `.env` в нём отсутствует.

### Настройка pre-commit хуков

В репозитории используются хуки [pre-commit](https://pre-commit.com/), чтобы автоматически запускать линтеры и автотесты.

В корне репозитория в **активированном виртуальном окружении** запустите команду для настройки хуков:

```shell
$ pre-commit install
pre-commit installed at .git/hooks/pre-commit
```

В последующем при коммите автоматически будут запускаться линтеры и другие проверки. Если проверки не пройдут, то коммит прервётся с ошибкой.

В репозитории настроены следующие хуки (файл `.pre-commit-config.yaml`):
- `check-added-large-files` — проверка размера добавляемых файлов
- `editorconfig-checker` — проверка соответствия `.editorconfig`
- `ruff` — проверка кода линтером

После установки хуков при коммите вы увидите их вывод:

```shell
$ git commit -m "Message"
check-added-large-files..............................................Passed
editorconfig-checker...............................................Passed
ruff................................................................Passed
[main 1a2b3c4] Message
 1 file changed, 1 insertion(+)
```

`Passed` означает, что проверка пройдена, а строки `[main ...]` — что коммит создан.

Чтобы запустить все хуки на всех файлах без коммита:

```shell
$ pre-commit run --all-files
```

Если вам потребуется сделать коммит без проверок, то вы можете отключить их с помощью флага `--no-verify`:
```shell
git commit -m 'Message' --no-verify
```

### Подключение фронтенда

Для ручного тестирования используется скомпилированный фронтенд.

Фронтенд разрабатывается и поддерживается отдельной командой в отдельном
репозитории. В репозиторий бекенда файлы фронтенда **не попадают**: они нужны
только для локального ручного тестирования. В проекте настроено игнорирование —
в `.gitignore` добавлена строка `static/`, поэтому вся папка `src/static/` не
отслеживается git-ом.

1. Скачайте [архив с фронтендом](https://dvmn.org/filer/canonical/1750917110/1035/).
2. Распакуйте архив и скопируйте содержимое папки `frontend/` в `src/static/`. В папке должны появиться файлы `index.html`, `assets/` и другие.
3. Убедитесь, что в `src/static/` есть файл `frontend-settings.json`:

```json
{
    "backendBaseUrl": "/frontend-api"
}
```

4. Запустите бекенд из корня репозитория:

```shell
$ fastapi dev src/main.py
```

5. Откройте в браузере главную страницу фронтенда:

http://127.0.0.1:8000/

Вы должны увидеть главную страницу FastAI.

Убедиться, что папка фронтенда игнорируется, можно так:

```shell
$ git check-ignore -v src/static/index.html
.gitignore:10:static/	src/static/index.html
```

Имя файла и номер строки (`.gitignore:10`) — строка в `.gitignore`, по которой
файл игнорируется. После коммита и отправки изменений в origin в последнем
коммите отсутствует папка `src/static/` — фронтенд относится исключительно к
локальной инсталляции.

### Запуск MinIO (S3)

Проект сохраняет сгенерированные сайты в S3-совместимое хранилище.
Локально для этого используется [MinIO](https://min.io/) (продукт AIStor).
Подробная инструкция по установке и активации лицензии — в
[README](/README.md#работа-с-s3-minio). Ниже — пошаговый чек-лист для
разработчика: пройдите шаги по порядку и проверьте результат.

#### 1. Установка

Скачайте deb-пакет MinIO (AIStor) и установите его — команды в разделе
«Установка и запуск MinIO» [README](/README.md#установка-и-запуск-minio).

Проверьте, что MinIO установлен:

```shell
$ minio --version   # выводит версию сервера
```

#### 2. Настройка и данные для авторизации

Настройте `/etc/default/minio` и укажите в `/etc/minio/config.env` учётные
данные и лицензию:

```shell
MINIO_ROOT_USER=<user>
MINIO_ROOT_PASSWORD=<password>
MINIO_LICENSE=<содержимое minio.license>
```

`MINIO_ROOT_USER` и `MINIO_ROOT_PASSWORD` — это также логин и пароль для входа
в веб-интерфейс.

#### 3. Запуск

Запустите сервис и проверьте, что он работает:

```shell
$ sudo systemctl enable --now minio
$ sudo systemctl status minio          # Active: active (running)
$ curl -sf http://localhost:9000/minio/health/ready   # → 200
```

#### 4. Адреса

- **API** — `http://localhost:9000`
- **Веб-интерфейс** — `http://localhost:9001`

При открытии адреса API в браузере происходит автоматический редирект в
веб-интерфейс.

#### 5. Вход в веб-интерфейс

Откройте `http://localhost:9001` и войдите под учётными данными
`MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`.

#### 6. Проверка бакета

В разделе **Buckets** найдите бакет `fastai-sites`:

- тип доступа у бакета — **PUBLIC**;
- список объектов пуст — первый объект появится после ручной загрузки или
  генерации сайта.

Если бакета ещё нет, создайте его через веб-интерфейс (имя должно быть равно
`S3__BUCKET_NAME`), при создании выбрав публичный доступ. Либо пропустите этот
шаг — бакет создастся автоматически при старте приложения (см. шаг 7).

#### 7. Настройка бэкенда

Заполните в `.env` группу `S3` (обязательна, значения по умолчанию смотрите
в `src/env_settings.py`):

```shell
S3__ENDPOINT_URL=http://localhost:9000
S3__ACCESS_KEY_ID=<MINIO_ROOT_USER>
S3__SECRET_ACCESS_KEY=<MINIO_ROOT_PASSWORD>
S3__BUCKET_NAME=fastai-sites
# Необязательные: таймауты и лимит подключений
S3__CONNECT_TIMEOUT=5
S3__READ_TIMEOUT=60
S3__MAX_POOL_CONNECTIONS=10
```

При старте приложения (`lifespan` в `src/main.py`) вызывается `ensure_bucket`:
он создаёт бакет, если его нет, и применяет публичную bucket-политику, поэтому
файлы доступны по прямой ссылке без авторизации.

#### Настройка Gotenberg (генерация скриншотов)

После каждой генерации сайта приложение рендерит его скриншот через
[Gotenberg](https://gotenberg.dev/): итоговый HTML отправляется в
`render_screenshot()` (`src/gotenberg_client.py`), а готовый JPEG загружается
в бакет через `upload_screenshot()` (`src/s3_client.py`) по постоянному ключу
`SCREENSHOT_KEY = "screenshot.jpg"`.

Заполните в `.env` группу `Gotenberg`:

```shell
GOTENBERG__ENDPOINT_URL=https://demo.gotenberg.dev
GOTENBERG__MAX_CONNECTIONS=5
GOTENBERG__TIMEOUT=10   # на 2-5 сек больше WAIT_DELAY
GOTENBERG__WIDTH=1280
GOTENBERG__WAIT_DELAY=8
GOTENBERG__DEFAULT_SCREENSHOT_FORMAT=jpeg   # png | jpeg | webp
```

Обязательна только `GOTENBERG__ENDPOINT_URL` — без неё приложение не
запустится (`ValidationError: gotenberg.endpoint_url Field required`).
Остальные настройки необязательны и имеют значения по умолчанию:

| Переменная | Обязательная | По умолчанию | Описание и выбор значения |
|---|---|---|---|
| `GOTENBERG__ENDPOINT_URL` | да | — | URL API Gotenberg. Стандартный публичный API — `https://demo.gotenberg.dev` (проверка доступности — `GET /health`); для локального сервера укажите свой адрес. |
| `GOTENBERG__MAX_CONNECTIONS` | нет | `5` | Лимит одновременных подключений. |
| `GOTENBERG__TIMEOUT` | нет | `10` | Таймаут клиента, сек. Берите на 2–5 сек больше `WAIT_DELAY`, иначе скриншот не успеет сняться. |
| `GOTENBERG__WIDTH` | нет | `1280` | Ширина скриншота, пикс. |
| `GOTENBERG__WAIT_DELAY` | нет | `8` | Пауза для загрузки анимаций страницы, сек. Для тяжёлых страниц увеличьте. |
| `GOTENBERG__DEFAULT_SCREENSHOT_FORMAT` | нет | `jpeg` | Формат скриншота: `png`, `jpeg`, `webp`. |

Если Gotenberg недоступен, `render_screenshot()` возвращает `None`: генерация
сайта продолжается, а на месте скриншота сохраняется прежнее изображение.

#### Ручная загрузка первых файлов

Фронтенд показывает превью сгенерированных сайтов: код HTML и скриншот. Ссылки
на эти файлы в коде формирует `_s3_urls()` в `src/routers/sites.py` и отдаёт их
в API как `htmlCodeUrl` / `htmlCodeDownloadUrl` / `screenshotUrl` — по ним
фронтенд загружает превью и картинку. Файлы должны лежать в бакете заранее,
иначе превью и скриншоты вернут `404` и фронтенд будет выглядеть сломанным.

Ручная загрузка файлов позволяет использовать ссылки на них при реализации
эндпоинтов: `GET /sites/my` и `GET /sites/{id}` возвращают `htmlCodeUrl`,
`htmlCodeDownloadUrl`, `screenshotUrl`.

Пока файлов нет в бакете, положите их вручную через веб-интерфейс
`http://localhost:9001` (Object Browser). По задаче в первую очередь в корень
бакета загружают демо-файлы:

- `index.html` — HTML демо-сайта;
- `index.png` — демо-скриншот.

Публичные адреса этих файлов (бакет `fastai-sites`):

```
http://localhost:9000/fastai-sites/index.html   — демо-сайт
http://localhost:9000/fastai-sites/index.png    — скриншот
```

Формат адреса: `{S3__ENDPOINT_URL}/{S3__BUCKET_NAME}/{key}`.

Ссылки, которые отдаёт код (`_s3_urls()` в `src/routers/sites.py`:
`htmlCodeUrl`, `htmlCodeDownloadUrl`, `screenshotUrl`), ведут на ключи
`sites/1/index.html` и `screenshot.jpg` — первый загружайте в папку `sites/1/`,
второй в корень бакета. Без них превью вернёт `404` и фронтенд будет выглядеть
сломанным.

```
http://localhost:9000/fastai-sites/sites/1/index.html   — HTML по ссылке из API
http://localhost:9000/fastai-sites/screenshot.jpg       — скриншот по ссылке из API
```

Загружать нужно один раз: после первой генерации сайта HTML и скриншот
заливаются приложением автоматически (`screenshot.jpg` перезаписывается
при каждой генерации).

#### Загрузка файлов из python-кода

Пример кодовой загрузки в бакет — `src/prototype_s3.py`. Он читает настройки
S3 из `.env`, создаёт бакет, применяет публичную политику и загружает файлы:

```shell
$ uv run python src/prototype_s3.py
```

При загрузке через `put_object` обязательно указывайте:

- `ContentType` — MIME-тип файла;
- `ContentDisposition="inline"` — файл открывается в браузере по публичной
  ссылке (без него браузер предложит скачать файл).

MIME-типы, используемые в проекте:

- `text/html` — HTML-файлы (например, `hello.html`, `sites/1/index.html`);
- `image/jpeg` — скриншоты (`screenshot.jpg`).

В коде приложения загрузка уже реализована в `src/s3_client.py`:

- `upload_html()` — указывает `ContentType="text/html"` и
  `ContentDisposition="inline"`;
- `upload_screenshot()` — указывает `ContentType="image/jpeg"` и
  `ContentDisposition="inline"`, загружает JPEG по ключу `screenshot.jpg`.

Публичные адреса после загрузки:

```
http://localhost:9000/fastai-sites/hello.html
http://localhost:9000/fastai-sites/screenshot.jpg
```

Ключи в бакете:

- `sites/{site_id}/index.html` — сгенерированный HTML сайта (перезаписывается
  при каждой генерации);
- `screenshot.jpg` — единый скриншот;
- `hello.html` — тестовый файл прототипа.

## Как вести разработку

### Схема приложения

Чтобы познакомиться с архитектурой FastAI, посмотрите схемы:

- Схема [локальной инсталляции бэкенда](https://gitlab.dvmn.org/root/fastapi-articles/-/wikis/fastai/backend_local_installation.drawio.png)
- Схема [продовой инсталляции бэкенда](https://gitlab.dvmn.org/root/fastapi-articles/-/wikis/fastai/backend_prod_installation.drawio.png)
- Схема [подсистем бэкенда](https://gitlab.dvmn.org/root/fastapi-articles/-/wikis/fastai/backend_decomposition.drawio.png)

Код проекта находится в папке `/src`.

Находясь в корневой директории проекта, запустить проект можно командой:

```shell
$ fastapi dev src/main.py
```

Проект будет работать по адресу http://127.0.0.1:8000/

Это **dev-режим**: `fastapi dev` запускает приложение с автоматическим
перезапуском при изменении исходного кода. Достаточно изменить и сохранить
любой `.py` файл — сервер сам перезапустится и подхватит изменения, вручную
останавливать и запускать его не нужно. В консоли при этом появится строка
`Detected file change in 'src/...py', reloading...`.

Для запуска без автоперезапуска (как в продакшене) используйте:

```shell
$ fastapi run src/main.py
```

### Как сделать коммит

Проверьте список изменённых и новых файлов:

```shell
$ git status
```

Добавьте изменения в индекс:

```shell
$ git add .
```

Создайте коммит:

```shell
$ git commit -m "Message"
```

Перед созданием коммита автоматически запустятся хуки: линтер Ruff и editorconfig-checker. Если все проверки пройдены, вы увидите `Passed` по каждому хуку и сообщение об успешном создании коммита:

```shell
check-added-large-files..............................................Passed
editorconfig-checker...............................................Passed
ruff................................................................Passed
[main 1a2b3c4] Message
```

Если проверки не пройдут, коммит прервётся. Например, при ошибке в коде Ruff выведет список проблем:

```shell
ruff................................................................Failed
- hook id: ruff
- exit code: 1

src/main.py:20:1: E402 Module level import not at top of file
src/main.py:25:13: B023 Function definition does not bind loop variable `i`
Found 2 errors.
```

В выводе:
- `ruff` и `hook id: ruff` — сервис, который вызвал ошибку
- `src/main.py` — путь к файлу с проблемой
- `20:1`, `25:13` — номер строки и колонки
- `E402`, `B023` — категория ошибки
- текст после кода — пояснение проблемы

Из-за `fail_fast: true` в `.pre-commit-config.yaml` при первой ошибке остальные хуки не запустятся. Исправьте ошибки, снова добавьте файлы в индекс и повторите коммит.

Если нарушен `.editorconfig` (например, в конце `main.py` нет пустой строки), вы увидите:

```shell
editorconfig-checker...............................................Failed
- hook id: editorconfig-checker
- exit code: 1

src/main.py
  text_final_newline (insert_final_newline): expected true, got false
```

В выводе:
- `editorconfig-checker` и `hook id: editorconfig-checker` — сервис, который вызвал ошибку
- `src/main.py` — путь к файлу с проблемой
- `text_final_newline` / `insert_final_newline` — правило из `.editorconfig` про пустую строку в конце файла
- `expected true, got false` — в файле нет завершающей пустой строки

Исправление: верните пустую строку в конец файла и сохраните его. Затем снова добавьте файл в индекс и повторите коммит.

Если вы случайно добавили в индекс большой файл (например, видео больше
`500 КБ`), коммит прервётся хук `check-added-large-files`:

```shell
check for added large files..............................................Failed
- hook id: check-added-large-files
- exit code: 1

stroy_big_video.mp4 (2048 KB) exceeds 500 KB.
```

В выводе:
- `check-added-large-files` и `hook id: check-added-large-files` — сервис, который вызвал ошибку
- `stroy_big_video.mp4` — путь к файлу с проблемой
- `(2048 KB) exceeds 500 KB` — пояснение: размер файла превышает порог

Коммит при этом **не создаётся**. Исправление: уберите большой файл из индекса
(`git restore --staged <файл>`) и удалите его из рабочего дерева, либо
отслеживайте его через Git LFS. После этого повторите коммит.

Если вы изменили только документацию (например, CONTRIBUTING.md) и не хотите ждать работу хуков, добавьте флаг `--no-verify`:

```shell
$ git commit -m "docs: описание правок" --no-verify
```

Перед коммитом хуки **не** запустятся — в выводе не будет строк `Passed`/`Failed`, только сообщение об успешном создании коммита:

```shell
[main 1a2b3c4] docs: описание правок
 1 file changed, 2 insertions(+)
```

Используйте флаг только для правок документации — для изменений кода хуки проходить обязательно.

### Как установить python-пакет в виртуальное окружение

В качестве менеджера пакетов используется [uv](https://docs.astral.sh/uv/).

Вот пример как добавить в зависимости библиотеку `beautifulsoup4`.

```shell
$ uv add beautifulsoup4
```

Если мажорные версии библиотеки несовместимы между собой и обновление может
сломать код, зафиксируйте конкретную версию при добавлении:

```shell
$ uv add 'beautifulsoup4==4.12.3'
```

Секреты фиксации версий:

- `==4.12.3` — жёстко зафиксировать версию (`pyproject.toml` получит `==4.12.3`);
- `~=4.12` — разрешить только патчи (совместимо с `4.12.x`, но не с `4.13`);
- без ограничений — uv выберет последнюю доступную версию.

Конфигурационные файлы `pyproject.toml` и `uv.lock` обновятся автоматически.

Проверить, какая версия библиотеки установлена в виртуальном окружении, можно
так:

```shell
$ uv pip list | grep beautifulsoup4
beautifulsoup4 4.12.3
```

`uv pip list` выводит список всех установленных пакетов с их версиями — это
версия, использованная при отладке кода в локальном окружении.

Аналогичным образом можно удалять python-пакеты:

```shell
$ uv remove beautifulsoup4
```

Если необходимо обновить `uv.lock` вручную, то используйте команду:

```shell
$ uv lock
```

#### Библиотека из Git-репозитория (не в PyPI)

Если библиотека отсутствует в PyPI, но есть публичный git-репозиторий
(например, собственная библиотека команды для генерации HTML-разметки),
укажите его как источник при добавлении:

```shell
$ uv add "html-page-generator @ git+https://github.com/devmanorg/html-page-generator.git"
```

После добавления:

- в `pyproject.toml` имя библиотеки появляется в списке `dependencies`, а в
  секции `[tool.uv.sources]` — ссылка на git-репозиторий:

  ```toml
  [tool.uv.sources]
  html-page-generator = { git = "https://github.com/devmanorg/html-page-generator.git" }
  ```

- в `uv.lock` пакет зафиксирован с версией и источником — git-URL с ревизией
  (commit), например:
  ```toml
  source = { git = "https://github.com/devmanorg/html-page-generator.git#74c84d935e3b3f318d4aa73e062452cd6811f767" }
  ```

В проекте так подключены `html-page-generator` и `gotenberg-api`.

Проверить установку из репозитория:

```shell
$ uv pip list | grep html-page-generator
html-page-generator 0.1.0
```

В сообщении об установке видно название, номер версии и источник:

```shell
$ uv sync --reinstall-package html-page-generator
~ html-page-generator==0.1.0 (from git+https://github.com/devmanorg/html-page-generator.git@74c84d9...)
```

### Проверка кода линтерами

Перед коммитом проверьте код линтерами:

```shell
$ make lint
```

Команда запустит [Ruff](https://docs.astral.sh/ruff/) — он проверит синтаксис, codestyle, порядок импортов и совместимость типов.

Что именно проверяет Ruff:

- **Синтаксис** — ошибки разбора файла (невозможно импортировать модуль);
- **Codestyle** — нарушения PEP 8 (правила `E`, `W` из `ruff.toml`);
- **Порядок импортов** — несортированный или неотформатированный блок импортов (правило `I`);
- **Типы и логику** — обращение к необъявленным именам (`F821`), опасные паттерны сравнения (`B`), несовместимые конструкции аргументов/типов возврата (`RET`, `PL`).

Набор активных правил задан в `ruff.toml`, поэтому проверки могут отличаться от стандартных настроек Ruff.

Если код соответствует всем правилам, Ruff закончит проверку без списка проблем — вы увидите:

```shell
$ make lint
ruff check ./src
All checks passed!
```

Строка `All checks passed!` означает, что отсутствуют ошибки синтаксиса, codestyle, порядка импортов и типов. Код возврата команды — `0`.

При наличии ошибок Ruff проверяет все файлы проекта и выводит каждую найденную проблему отдельной строкой. Ошибка порядка импортов выглядит так:

```shell
src/main.py:1:1: I001 [*] Import block is un-sorted or un-formatted
Found 1 error.
[*] Fixable with `ruff check --fix`.
```

Формат строки: `файл:строка:колонка: код ошибки [*] описание`. Код `I001` означает неправильный порядок импортов. В конце проверки Ruff выводит статистику — общее количество найденных ошибок.

Если линтер найдёт ошибки, которые можно исправить автоматически, запустите автоформатер:

```shell
$ make format
```

После этого повторите `make lint`, чтобы убедиться, что все ошибки исправлены.

### Форматирование кода

Перед коммитом отформатируйте код с помощью Ruff.

Посмотрите, какие изменения предлагает внести Ruff:

```shell
$ ruff format --diff .  # посмотреть, что изменится
```

Ruff выводит diff в формате `--- src/file.py` / `+++ src/file.py` — какие строки
изменит. В конце — статистика, например:

```shell
1 file would be reformatted, 8 files already formatted
```

Примените изменения:

```shell
$ ruff format .  # применить изменения
```

Ruff отформатирует файлы и выведет список изменённых файлов:

```shell
1 file reformatted, 8 files already formatted
```

`1 file reformatted` — файл был изменён, `8 files already formatted` — остальные
файлы уже соответствовали правилам и не требовали правок. Успешным считается
завершение с кодом возврата `0`.

Исправьте всё, что можно исправить автоматически:

```shell
$ ruff check --fix .  # исправить, что можно
```

### Ошибки форматирования и сложности кода

Если Ruff сообщает об ошибке, проверка будет выглядеть так:

```shell
src/main.py:10:5: C901 `process_request` is too complex (11 > 7)
```

Формат строки:
- `src/main.py` — путь к файлу с ошибкой
- `10:5` — номер строки и колонки
- `C901` — код ошибки высокой цикломатической сложности
- `(11 > 7)` — текущее значение сложности и допустимый порог из `ruff.toml` (`max-complexity = 7`)

Такие ошибки автоматически не исправляются — упрощайте код вручную: разбивайте функции, выносите ветвления.

**Особые случаи в FastAPI:**
- Декораторы с многострочными параметрами — соблюдайте правила переноса строк
- Pydantic модели — длинные аннотации типов форматируйте вручную
- Async/await конструкции — большие async-функции разбивайте на части

### Команды для быстрого запуска с помощью make

Для вывода списка часто используемых коротких команд используйте команду

```shell
$ make list
Cписок доступных команд:
lint                          Проверить линтерами код в репозитории
format                        Запустить автоформатер
list                          Отобразить список доступных команд и их описание
```

`make list` выводит каждую команду и её описание без запуска самой команды.
Команда завершается успешно (код возврата `0`, ошибок в выводе нет) и полезна,
когда нужно вспомнить, что делает `lint` или `format`.
